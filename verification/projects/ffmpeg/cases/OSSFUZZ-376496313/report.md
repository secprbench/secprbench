## Findings

- The same Docker reproducer triggered a sanitizer or race report only after introduction.
- Root cause confirmed exactly as described in meta.json / the fix commit message. In mxf_edit_unit_absolute_offset() (libavformat/mxfdec.c), the intro commit's fast-path clamp `edit_unit = FFMAX(FFMIN(edit_unit, index_end), first_segment->index_start_position);` mixes the signed local `edit_unit`/`index_end` with the *unsigned* struct field `index_start_position` (declared `uint64_t`). Because of this signed/unsigned mixing, FFMAX(INT64_MIN, 0u) keeps the huge-unsigned reinterpretation of INT64_MIN instead of clamping edit_unit back to a sane non-negative value, so edit_unit can end up being INT64_MIN even though the "clamp" was supposed to bound it to the index's real range.

I crafted an index table with two IndexTableSegments for the same IndexSID/BodySID: segment B's IndexStartPosition=-1 and IndexDuration=INT64_MIN make av_sat_add64(-1, INT64_MIN) saturate to exactly INT64_MIN (this becomes `index_end`). With the natural small edit_unit query (0/1) that mxf_set_current_edit_unit passes on the very first packet, the buggy clamp collapses to exactly INT64_MIN. That value then matches segment A's range (segment A's IndexStartPosition=0, IndexDuration=2^63+1, which in *unsigned* terms is bigger than INT64_MIN's unsigned reinterpretation, so the `edit_unit < s->index_start_position + s->index_duration` check — done in unsigned arithmetic since index_duration is uint64_t — passes). This gives `index = edit_unit - s->index_start_position == INT64_MIN`, and because IndexEntryArray count (3) was chosen so `nb_index_entries == 2*index_duration+1 (mod 2^64)`, the "Avid index" branch executes `index *= 2;` on INT64_MIN, a signed integer overflow.

Reproduced via run.sh (self-contained: builds the base MXF, patches in the two malicious segments, recompiles libavformat/mxfdec.c with -fsanitize=address,undefined -fno-sanitize-recover=undefined since this harness's default build only has ASan, relinks ffmpeg, then demuxes the file):
- post_intro (649ac17efd96): CRASHES — "libavformat/mxfdec.c:1950:27: runtime error: signed integer overflow: -9223372036854775808 * 2 cannot be represented in type 'long'", with call stack mxf_edit_unit_absolute_offset -> mxf_set_current_edit_unit -> mxf_read_packet -> ff_read_packet -> avformat_find_stream_info, exactly matching the original OSS-Fuzz crash state (mxf_edit_unit_absolute_offset / mxf_set_current_edit_unit / mxf_read_packet) and its "2 * -4962931467012268000" (negative-value-doubled) signature.
- pre_intro (e3fa469a55a0, old per-segment `edit_unit = FFMAX(edit_unit, s->index_start_position)` loop that never pulls edit_unit below the original non-negative query): completes cleanly, exit 0, no sanitizer report, using the identical crafted file.
- post_benign (fix commit f7cc023f06c4's `if (edit_unit < 0) return AVERROR_PATCHWELCOME;` guard applied): completes cleanly, exit 0, no sanitizer report, using the identical crafted file.

Same reproducer (same run.sh / same generated bytes) used unchanged across all three revisions, only the sanitizer-augmented rebuild step differs is identical, and the crash is a genuine target-code UBSan report (not a harness artifact), so intro_verified=yes and benign_verified=yes.
